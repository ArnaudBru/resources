The practical one-pager protocol

How to write a 1–2 page reference that's worth coming back to. Five pre-flight questions, structural conventions, and the rules that emerged from building two pagers iteratively.

TL;DR

  • Ask 5 pre-flight questions before opening an editor. Wrong answers on audience, shape, or specificity force a full rewrite — cheap to ask, expensive to skip.
  • Title the page by the question it answers, not the underlying concept. "How to choose an instance" ages better than "Memory estimation".
  • Each idea appears once. Tables for scan, prose for stories, lists for enumerations. Pair formula tables with concrete-reference tables; pair frameworks with worked examples.
  • Variable names match across TL;DR, tables, and examples. No N / B / pf without a legend.
  • Self-contained HTML, inline CSS, no JS, no CDN. Works offline. Lives in ~/Desktop/plans/html/.

1Pre-flight questions — ask these before writing anything

Five questions, in this order. Each answer eliminates a design space. Skip them and you'll write a page that the audience can't use.

QuestionWhat it shapesCommon answers and what they imply
1. Audience Density, jargon level, explanation depth. Me only → max density, no apologies. Team → onboarding-quality, define vocabulary inline. Mixed (me + team + hires) → default; density preserved, explanations terse but present. External → lighter on jargon, more framing.
2. Usage context Length budget, layout style. On-screen during debugging → scrollable rich layout, Cmd-F-friendly. Printed / wall → one page; ruthless cut. Linked from tickets → deep-linkable sections; bookmark-friendly. Onboarding → longer OK; first-read flow matters.
3. The question this page answers in one sentence The title. The structure. What gets cut. Write the title as the question, not the concept. "How do I choose the right instance?" rather than "Memory estimation". If you can't write it in one sentence, you don't yet know what the page is for.
4. Specificity How project-coupled the body is. Generic → reusable; project references break tone. Generic + example (default) → page reads as concepts with a labelled "Example" sidebar grounding it. Project-coupled → the project IS the value-add (rare; usually a sign you wanted a project doc, not a one-pager).
5. Shape Top-of-page structure. Decision-guide → framework / decision tree at top, sequential sections, "pick which" logic. Reference → comparison tables dominate, no decision tree needed. Analysis & recommendation → TL;DR-heavy, findings before prescriptions, side notes for orthogonal levers.

2Structural conventions — section order, top to bottom

Every page is some subset of these blocks, in this order. Skip optional ones if they don't earn their space.

BlockStatusPurpose
Title + 1-line subtitlerequiredThe subtitle answers what question this page answers. The title is the question.
TL;DR boxanalyses / references3–5 bullets max. Includes the dominant formula's full variable names. Readers screenshot this.
Framework / decision treedecision-guidesNumbered lenses or steps applied in order. Eliminates "pick by cost first" mistakes.
Reference tablesrequiredThe core scan layer. Formulas with intuition cells. Concrete priors at recognisable workloads.
Worked example (boxed)requiredOne named example. Dashed-border box, "EXAMPLE" label. Clearly skippable for readers who only want the framework.
Pitfalls / gotchasrequiredSpecific failure modes + how to recognise + how to fix. Amber-tinted box.
References / further readingoptionalLinks to deeper material. Keep tight; not a dumping ground.

3Density and content rules

Each idea in exactly one place

  • If the same component is in a formula table and a separate prose "what this is" section, you have two copies. Cut the prose; add a "What it is" cell to the formula table instead. One row per idea, formula + intuition side-by-side.
  • Exception: an idea that genuinely needs two reading modes (table for scan, paragraph for first-time learners) can be in both — but mark which is which.

Pick the right structure per content type

  • Tables when content is parallel (4+ rows of the same shape). Comparisons, formulas, configs.
  • Prose when there's causality or a story ("this happened because…").
  • Bulleted lists for enumerations that aren't structured enough for a table.

Variable naming

  • Use the same names in formulas as in the TL;DR, never abbreviate. batch_size, not B. num_workers × prefetch_factor, not w × pf.
  • The asymmetry: you wrote the abbreviations, so they feel obvious. The first-time reader hasn't lived in your head. They pay a translation cost on every formula.

Hedge consistently

  • If one scaling claim is hedged ("linear until vCPU saturates"), hedge all of them. Mixed precision signals "the writer didn't notice."
  • "Proportional speedup" and "linear speedup" describe the same math. Pick one term, use it everywhere.

Pair formulas with concrete numbers

  • Formula tables tell you the dimensions; ballpark tables tell you the magnitude. Readers need both: "VRAM ∝ batch × activations" and "ResNet-50 at bs=64 ≈ 6 GB".
  • Call out non-obvious modality shifts where the dominant term changes (activations dominate vision; weights dominate LLMs).

Replace metaphors with measurements

  • "The smoking gun" → "CPU 680 % / GPU ~0 %". Readers trust numbers more than phrases.
  • If you can quote a measurement, do. Reserve metaphor for cases where no measurement exists.

4Visual and tech baseline

Tech

  • One .html file, inline <style>, no external CDN or build step. Works offline.
  • Markdown-readable structure where reasonable (headings, paragraphs, lists). Hand-crafted HTML only where the visual layout pays for itself (tables, callout boxes, decision-tree numbering).
  • Save at ~/Desktop/plans/html/<slug>.html.

Layout

  • Two-column ONLY when content is genuinely parallel (VRAM ∥ sys RAM are two independent capacities; framework steps are not parallel — they're sequential).
  • Default to single-column flow. Two-column is a feature, not a default.
  • Numbered section circles for sequential frameworks (lenses, steps).

Colour palette (the v2 reference set)

  • Ink (text) / muted (subtitles, intuition cells) / paper (background)
  • Ok / warn / bad for pills and status — sparingly
  • Section accents only when a section maps onto a real distinction (VRAM blue, sys RAM amber, etc.) — not for visual variety
  • One callout style per block type: TL;DR = left-bar card; Example = dashed-border sidebar with "EXAMPLE" label; Gotchas = amber-tinted box. Don't invent new ones per page.

5Iteration rules — extracted from real feedback

These rules came out of building two pages and listening to where they didn't work. They're the ones a v0 methodology would have missed.

RuleTrigger
Title from the question v2 was initially titled "Training memory estimation". Real question turned out to be "How to choose the right instance" — memory is one of four lenses. Renamed the page and restructured around the question. Methodology rule: start by writing the question the page answers, derive the title from it, derive sections from the title.
Name decision variables in the TL;DR TL;DR originally said "scales with dataloader config". Reader noticed batch_size wasn't mentioned. Fixed to num_workers × prefetch_factor × batch_size × per_sample_peak. If a formula's parameters are decision variables for the reader, name them all in the TL;DR. Don't hide drivers behind "config".
No single-letter abbreviations Formula tables used N × dtype_B and B × A_sample × dtype_B. Reader asked what B and A_sample meant. Use full descriptive names in formulas, identical to those in the TL;DR.
Pair formulas with concrete priors Components table told you VRAM ∝ batch × activations but didn't tell you whether ResNet-50 needs a T4 or an H100. Added an "Orders of magnitude" table with 9 classic backbones. Formulas are dimensions; priors are magnitudes. Both are needed.
Hedge consistently Wrote "linear speedup until vCPU saturates" for workers, but "proportional speedup" (no hedge) for GPU upgrades. Same math, mixed terminology. Pick one scaling word, hedge it the same way every time it appears.
Replace metaphors with measurements Used "the smoking gun" to describe a CPU/GPU utilisation ratio. Reader: "blabla is the smoking gun is metaphorical". Replaced with the numbers themselves. If a number can carry the claim, let it.
Subcategorise multi-option lists Recommendations table had 4 rows, all marked with savings × effort, but didn't separate "removes the bottleneck" from "fewer steps" from "lower $/h". Grouped into three subcategories. When options differ in their mechanism, group by mechanism — don't flatten into a single list.
Generic body, project example v1 mixed S3D specifics into the main flow. v2 confined S3D to a labelled "Example" sidebar; the main text reads generically. Body answers the general question; one boxed sidebar anchors it in a real case.
Build inductively, refine through feedback A polished v0 methodology written upfront over-engineers. v0 + iteration + extraction is faster and produces sturdier rules. Methodology is the residue of iteration, not the seed.
Match paragraph styling to purpose In the dataset-strategies page, the decision-flow intro paragraph was muted / 13 px (section-framing style) but contained substantive content (5 shortcut categories the reader needs to recognise). Reader flagged it as "not very nice". Bumped to body ink / 14 px with the categories bold-inline. Rule: framing styles for framing; body styles for content. Don't bury content under framing.
CSS Grid for columns, Flex for row rhythm Decision-flow list used Grid with a 1fr column for the question text. Result: phantom whitespace between question end and the arrow, varying per row based on text length — looked like "inconsistent spacing between words". Switched to Flex with gap: 10px; rows now have consistent inline rhythm at the cost of variable row width. Rule: Grid only when column alignment is load-bearing; Flex for inline rhythm. 1fr in Grid creates phantom whitespace whenever content widths vary.

What to cut — tempting things that rot the page

  • A separate "definitions" section that re-states what the formula table already says. The duplication looks educational but doubles the line count.
  • Concept-name titles ("Memory estimation", "PyTorch dataset strategies"). Find the question the reader is asking when they reach the page; title accordingly.
  • Single-letter variables without a legend. They feel obvious to the writer and opaque to the reader.
  • Metaphors when measurements exist. "It's the smoking gun" is weaker than the numbers it refers to.
  • "Useful tips" piles that aren't a real grouping. If you have 8 tips, ask whether they cluster into 2–3 categories.
  • Project narration in the main flow. "We ran this on AIW-3499 and saw…" belongs in the labelled Example sidebar, not paragraph 3 of the framework.
  • External JS or CDN dependencies. If the page only works online, it fails the offline-during-debugging use case.
  • A "Further reading" list of every paper you've ever cited. Three pointers. Five at most. Else delete the section.
