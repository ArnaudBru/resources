How to choose the right instance for model training

Given a model + batch + workload, what's the cheapest box that finishes in tolerable wall clock?

TL;DR

  • Four lenses must all pass: capacity (VRAM + sys RAM), throughput (compute regime), cost (incl. quota). Pick the smallest instance where all four pass.
  • VRAM = weights + grads + optimizer state + activations (dominant; linear in batch_size × model_depth × dtype). bf16 autocast gives ≈ ×0.55 the fp32 footprint.
  • Sys RAM = DataLoader queue (linear in num_workers × prefetch_factor × batch_size × per-sample_peak) + per-worker process overhead. Per-sample peak is 2-3× the on-disk size after augmentation.
  • Compute regime (GPU-bound vs dataloader-bound) is a throughput question. It tells you whether a bigger GPU helps or a bigger host helps — different fixes.
  • Cost has a quiet trap: spot pricing is ~3× cheaper, but spot quota is per-(account, region, instance, mode) and is often zero on newer GPU classes. Check before you plan around it.

The framework — four lenses, applied in order

  1. 1VRAM ceiling — which GPUs fit the model + batch? Eliminates GPU classes that are too small.
  2. 2Sys RAM ceiling — which host sizes fit the DataLoader queue + workers? Eliminates instance sizes that are too small.
  3. 3Compute regime — is the workload GPU-bound or dataloader-bound? Tells you which knob has any effect at all (bigger GPU vs more vCPU).
  4. 4Cost — among survivors of 1-3, pick the cheapest. Check spot quota before assuming spot pricing.

Reverse order trades off correctness: if you pick by cost first, you'll keep landing on instances that don't fit.

1VRAM (which GPUs fit the model + batch)

Capped by the GPU: T4 = 16 GB · A10G / L4 = 24 GB · A100 = 40 / 80 GB · H100 = 80 GB.

Components

ComponentFormulaWhat it is
Model weights params × bytes Float values on-GPU per param. fp32 = 4 bytes/param; bf16/fp16 = 2 bytes.
Gradients params × bytes One value per param holding ∂L/∂param. Created by backward(), consumed by optimizer.step().
Optimizer state (AdamW) params × 8 bytes Two fp32 moments per param. Stays fp32 even under bf16 autocast — the "master copy" of training.
Activations batch_size × activations_per_sample × bytes Layer outputs kept for backward. Dominant term. activations_per_sample grows with model depth × feature-map size — bigger model or higher input resolution = more.
CUDA context ~1–2 GB Per-process driver + cuDNN/cuBLAS + allocator pool. Independent of model size.
Fragmentation ~5–15 % Caching allocator never returns 100 % of chunks. Headroom for re-pack.

Useful ratios

  • bf16 vs fp32: halves weights + grads + activations. Net VRAM ≈ ×0.55.
  • Activation checkpointing: ~50 % activation memory for ~25 % step-time cost.
  • Batch scaling: ~linear in activations. bs=4 @ 15 GB → bs=8 ≈ 24 GB (OOMs on 24 GB cards).

2Sys RAM (which hosts fit the dataloader)

Capped by the instance. SageMaker g6.* on AWS: xlarge = 16 GB · 2xlarge = 32 · 4xlarge = 64 · 8xlarge = 128.

Components

ComponentFormulaWhat it is
DataLoader queue num_workers × prefetch_factor × batch_size × per_sample_peak FIFO of decoded batches in multiprocessing shared memory. Dominant on video / large-tensor pipelines.
Worker processes num_workers × (1–3 GB) Each is a forked Python with its own ffmpeg / torchvision state. Grows over training (GC lag).
Pin-memory thread ≥ 1 batch_size worth Copies batches to page-locked RAM for async GPU transfer. Required for non_blocking=True.
Augmentation transients 2–3 × on-disk_size per sample Rotate / resize buffers + uint8→fp32 cast (4×). Peaks co-exist with in-flight clips.
FastFile / OS cache 1–4 GB S3 FUSE + Linux page cache hold recently-read bytes. Speeds later epochs but consumes RAM.
Main process ~2–3 GB Training script's Python + CUDA driver libs + iterator state. Floor before any work.

Useful ratios

  • persistent_workers: skips per-epoch teardown. Workers stay warm but memory creeps.
  • prefetch_factor: linear queue scaling. 2 → 1 halves queue RAM, less burst tolerance.
  • num_workers: linear in both queue and worker overhead. Doubling ≈ doubles sys RAM.

3Compute regime: GPU-bound or dataloader-bound?

Tells you whether the next $/h goes into a bigger GPU or a bigger host. Two workloads with identical memory footprint can want opposite instance upgrades.

How to tell

SignalGPU-boundDataloader-bound
Per-step time ≈ GPU theoretical floor (FLOPs / chip TFLOPS at workload dtype) ≫ GPU floor (often 5-50×)
GPU util (CloudWatch / nvidia-smi) 60-100 % sustained < 30 % (often near 0 % at minute granularity)
CPU util Low to medium High; saturating vCPU
Effect of more num_workers None (bottleneck is GPU) ~Linear speedup until vCPU saturates
Effect of bigger GPU (more TFLOPS) Proportional speedup Nothing
Effect of more vCPU + sys RAM Nothing Speedup until pipeline saturates

Implication for instance choice

  • GPU-bound: upgrade the GPU class (T4 → A10G/L4 → A100). Same family but better tensor cores can be 2-3×. Bigger host is wasted.
  • Dataloader-bound: upgrade the host (more vCPU + sys RAM) and/or fix the data path (more workers, pre-decode, lighter augmentation). Bigger GPU is wasted.
  • Diagnose before you spend: a smoke run + a glance at GPU util is faster than guessing.

4Cost (spot, quota, $/h)

Among the candidates that passed 1-3, cost picks the winner. Two non-obvious facts dominate.

Spot is ~3× cheaper, when you can get it

  • Spot vs on-demand: typically a 60-70 % discount.
  • Spot quota is per-(account, region, instance type, mode). Often zero on newer GPU classes until you ask. Check before you plan around it: aws service-quotas list-service-quotas --service-code sagemaker --region <r>.
  • Quota requests are free and granted in hours-days. File early if you might need it.
  • Spot is preemptible — pair with checkpointing if jobs are long.

Cheaper-per-hour ≠ cheapest job

If your workload is dataloader-bound, a smaller-cheaper instance may finish slower than the per-hour ratio suggests. Run the per-step × total-steps × $/sec math, not just $/h.

Example3D-CNN video classifier on AWS SageMaker

~12 M-param video 3D-CNN (I3D class), 64-frame 224² clips, bs=4, bf16 autocast, video augmentations. Applying the four lenses:

LensResult
1 VRAM bs=4 bf16 ≈ ~13-15 GB → any 24 GB GPU works (A10G, L4). T4 (16 GB) fits at bs=4 fp32 only — no bf16 → loses ~2× throughput.
2 Sys RAM workers=4, prefetch=2 → ~37 GB peak (queue dominates: 4 × 2 × 4 × ~0.7 GB after augmentation). g6.2xlarge (32 GB) OOMs. g6.4xlarge (64 GB) floor.
3 Regime Per-step 4.25 s vs ~0.3-0.5 s GPU floor → strongly dataloader-bound. CloudWatch confirms: GPU util ~0 %, CPU util ~680 %. More vCPU helps; bigger GPU doesn't.
4 Cost g6 spot quota = 0 in eu-west-3 (above xlarge size). On-demand only. ml.g6.4xlarge OD at ~$2.50/h. (g6.2xlarge OD wk=2 would be cheaper per hour but ~2× slower per step → projects to a more expensive baseline.)
Decision ml.g6.4xlarge on-demand — smallest box where all four lenses pass.

Pitfalls

  • Picking the biggest box "to be safe" — wastes 2-3× $/h on capacity you don't use. Memory and regime tell you the floor; bigger is not always better.
  • Picking the smallest box because it's cheapest — OOMs cost a re-run, and one re-run usually wipes any savings. Worse: the failure may show up at hour-10 of a multi-day baseline.
  • Assuming spot is available — check quotas explicitly. Many newer GPU classes are zero spot quota in your region until requested.
  • Confusing VRAM OOM with sys-RAM OOM — different fixes, different upgrade direction. Read the Python traceback: CUDA OOM → VRAM; DataLoader worker exited → sys RAM.
  • Static memory estimates underestimate peak sys RAM by ~20-30 % on video pipelines (augmentation transients). Add a margin or instrument.
  • Bigger GPU when dataloader-bound — buys nothing. Profile GPU util first. A 0 % GPU on a $5/h box is worse than a 50 % GPU on a $1.50/h box.
  • $/h ≠ $/job. A cheaper-per-hour box with a slower per-step can finish more expensively. Compute the full per_step × total_steps × $/sec.
