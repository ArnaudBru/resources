How to choose the right PyTorch dataset pattern

Picking among in-memory, lazy-read, pre-decoded, sharded, feature-cached, and streaming — by data size, iteration speed, and training shape.

TL;DR

  • Six patterns, but really three axes: where the data lives (RAM / local disk / cloud / stream), what's pre-computed (nothing / decoded tensors / features / all of it), and access shape (indexable vs streaming).
  • Default to a map-style Dataset reading files lazily. It's the most flexible baseline; everything else is an optimisation earned by hitting a wall.
  • Pre-compute more (pre-decoded tensors, pre-extracted features) when you'll do many epochs and decode is the per-step bottleneck.
  • Shard or stream (WebDataset, IterableDataset) only when data is genuinely large-scale / distributed, or genuinely unbounded.
  • Pitfalls are mostly cross-pattern: worker fork pitfalls, augmentation seeding, decode speed, S3 throughput, distributed sampling. Apply regardless of which pattern you pick.

Decision flow — apply in order, first match wins

The earlier rows are shortcuts for specific shapes — small data, frozen backbone, streaming source, heavy decode, large-scale distributed. Most workloads fall through to the default.

  1. Does the whole dataset fit comfortably in RAM (≲ 10 GB single-machine)? → In-memory
  2. Training only a small head with a frozen backbone? → Pre-extracted features
  3. Data is a true stream / generator (Kafka, RL trajectories, infinite corpus)? → IterableDataset
  4. Many epochs AND decode is slow (video, high-resolution images)? → Pre-decoded tensors
  5. ≫ 100 k samples in cloud storage + distributed training? → Sharded (WebDataset / TFRecord)
  6. Anything else — full fine-tune on disk/cloud data, single machine: → Map-style + lazy read (default)

Comparison at a glance

What you spend (upfront, RAM, disk) vs. what you get (epoch speed, reusability).

Pattern Pre-compute cost First-epoch speed Steady-state speed RAM Disk Reusable across runs?
In-memory none instant fastest full dataset — per-process only
Map-style + lazy read none slow (cold cache) I/O + decode-bound minimal — via the source files
Pre-decoded .pt one decode pass slow (one-shot) fast (just torch.load) minimal large (~10× mp4) yes — disk artifact

The patterns in detail

1In-memory

Used for: MNIST, small tabular sets, sentence-pair fine-tuning, cached embeddings.

Use when

  • Dataset fits comfortably in RAM (typically ≲ 10 GB), single machine.
  • You want the absolute fastest steady-state iteration.
  • You'll re-shuffle / random-sample heavily across epochs.

Avoid when

  • Multi-GPU distributed (each GPU duplicates the dataset → 8× RAM).
  • Data ≳ 50 % of RAM (you'll OOM during peak augmentation transients).
  • You need to share/persist the loaded artifact.
Pattern: load everything into a list[Tensor] or single concatenated tensor in __init__; __getitem__ just indexes.

2Map-style + lazy read (the default)

Used for: image classification on ImageNet, video clips from mp4, audio from wav, anything where decode-at-training-time is acceptable.

Use when

  • Files live on local disk or cloud (S3, GCS) and you want zero upfront prep.
  • You'll fine-tune end-to-end and need raw inputs for augmentation flexibility.
  • Random sampling needs to be cheap (the index-to-file map is in memory).

Avoid when

  • Decode dominates per-step time and you do many epochs (consider pattern 3 or 4).
  • Data is so large that even indexing it is expensive.
Pattern: __init__ stores a list of file paths + labels; __getitem__ opens the file, decodes, augments. Tuning knobs: num_workers ≈ CPU count − 1; persistent_workers=True; prefetch_factor=2-4. First epoch is slow; the OS page cache warms it.

3Pre-decoded .pt on disk

Used for: long video-classification fine-tunes, repeated training over the same image dataset, hyperparameter sweeps where decode would dominate.

Use when

  • You'll iterate many times (sweeps, long fine-tunes) so the one-time decode pays back.
  • Local SSD has room (typically 5–10× the raw encoded size).
  • Augmentations can be expressed on tensors, not raw frames.

Avoid when

  • You're still iterating on input resolution or frame count (every change forces a re-decode pass).
  • Storage is constrained — raw uint8 tensors are huge vs. mp4.
Pattern: a one-shot prepare_dataset.py loops through, decodes, saves <id>.pt (or a sharded dict {id: tensor} for small datasets); __getitem__ just torch.load(f"{root}/{id}.pt"). Tensors should be pinned / float16 to keep size down.

4Sharded streaming (WebDataset / TFRecord)

Used for: large-scale pretraining (LAION-style image-text, video pretraining at scale), distributed multi-GPU / multi-node training.

Use when

  • ≫ 100 k samples, primarily in cloud storage (S3, GCS).
  • Distributed training (multi-node) — shards distribute cleanly across workers.
  • Access pattern is sequential-friendly (cloud reads are way faster sequentially).

Avoid when

  • You need to subset / sort / random-sample by attribute (sequential reads ≠ random access mid-shard).
  • Dataset is small enough that the sharding pass costs more than it saves.
Pattern: the webdataset library packages samples into .tar shards (or .tar.gz / .parquet). Each shard is read sequentially. For C++-speed decode pipelines, layer NVIDIA DALI on top.

5Pre-extracted features

Used for: CLIP / DINOv2 linear probes, fast head-architecture iteration, embedding-based retrieval pipelines.

Use when

  • Doing linear probing or training only a small head — backbone is genuinely frozen.
  • You want to iterate on the head in minutes per epoch on CPU.
  • No temporal / visual augmentation needed (or augmentations can be baked into preprocessing).

Avoid when

  • You want any end-to-end accuracy from unfreezing the backbone (this pattern locks it).
  • Augmentations need to vary per epoch — features are pre-computed once.
Pattern: a one-shot inference pass with a pretrained backbone; save {name: feature_vec} as a single .pt or .npy. Features are typically 768–4096 dim → ~1 MB per 1000 samples. Whole feature dataset usually fits in RAM (collapses to pattern 1).

6IterableDataset (streaming / generator)

Used for: RL trajectories, real-time data feeds (Kafka, message queues), very-large pretraining corpora where indexing the whole thing is impractical.

Use when

  • The data source is genuinely streaming (you can't pre-enumerate it).
  • The per-sample cost of being indexable would be prohibitive.
  • You want online sampling / on-the-fly generation.

Avoid when

  • You can list your data upfront and want clean epoch semantics — use map-style.
  • You want easy random sampling — IterableDataset doesn't natively support it.
Pattern: subclass IterableDataset with an __iter__ generator. Sharding across DataLoader workers is manual (worker_init_fn + offset / skip), so for >1 worker you must hand-shard the stream.

Common pitfalls (apply across patterns)

PitfallFix
Worker fork copies the whole Dataset object (S3 client, DB connection) Lazy-init network clients inside __getitem__, or use worker_init_fn — not __init__
Random transforms identical across workers (same seed) torch.manual_seed(base_seed + worker_id) in worker_init_fn
JPEG / mp4 decode is the bottleneck Use Pillow-SIMD or torchvision.io.read_image for JPEG; decord or torchvision.io.read_video for video
Augmentations are CPU-bound at higher batch sizes Move to GPU with kornia.augmentation or NVIDIA DALI
S3 throughput cap on first epoch Local LRU cache (e.g., 50 GB on SSD) — first epoch warms it, later epochs hit local
Class imbalance WeightedRandomSampler(weights, num_samples=…, replacement=True) — independent of dataset pattern
Distributed sampling DistributedSampler(dataset, shuffle=True) for map-style; WebDataset shards natively across ranks
Mixed dtypes (uint8 vs fp32) silently doubling memory Keep tensors in uint8 until the very end; convert + normalise inside the GPU forward when possible
Workers exit unexpectedly mid-training Almost always a host-RAM OOM, not a code bug — see the training-memory one-pager for diagnosis
