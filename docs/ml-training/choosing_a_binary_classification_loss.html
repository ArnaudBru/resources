Which loss for binary classification — BCE vs CE, with vs without logits?

A 2×2 decision matrix: loss family (BCE vs CE) on one axis, implementation form (with-logits vs without) on the other. The "with logits" diagonal is always right; the family choice depends on output shape and extensibility.

TL;DR

  • Always use the "with logits" variant (BCEWithLogitsLoss or CrossEntropyLoss). Mathematically equivalent to the non-logits form in fp32; required in fp16/bf16 autocast — non-logits variants produce log(0) = -inf when probabilities round to 0/1 in low precision.
  • BCE vs CE for binary classification: equivalent math, different shape. BCE expects (B,) or (B,1) logits with float targets; CE expects (B, 2) logits with integer class targets. Same gradient flow, same accuracy at convergence.
  • Pick by your model's output shape: num_classes=1 → BCEWithLogitsLoss; num_classes=2 → CrossEntropyLoss. Most pretrained backbones (ResNet, ViT, S3D) ship with C-output heads → CE is the drop-in.
  • Pick by intended extensibility: CE extends trivially to num_classes=N; BCE-per-class extends to multi-label (mutually inclusive classes). Single-label N-class with BCE doesn't make sense.
  • Class imbalance handling: CE uses a per-class weight vector; BCE uses a scalar pos_weight. Both work; pick the one whose API matches your loss family.

2Decision guide — pick the form first, then the family

Form (with-logits vs without) is a stability question with a near-universal answer. Family (BCE vs CE) is an architecture question that depends on your output shape and future plans.

Step 1 — Lock the form: "with logits"

Unless you're integrating a pre-existing model that already outputs probabilities and you cannot move the activation, use the with-logits variant. The cost is zero; the benefit is correctness under mixed precision.

Step 2 — Pick the family by output shape

If your model outputs…UseTarget shape + type
(B, 1) or (B,) — single logit per sampleBCEWithLogitsLoss(B,) float in {0., 1.}
(B, 2) — two logits per sample (one per class)CrossEntropyLoss(B,) long in {0, 1}
(B, N) with N > 2 — multi-class single-labelCrossEntropyLoss(B,) long in {0, …, N−1}
(B, N) with N > 1 — multi-label (mutually inclusive classes)BCEWithLogitsLoss applied per-class(B, N) float in {0., 1.}^N

Step 3 — Re-shape the model if neither family fits ergonomically

If you're building from scratch and have no constraint, the "natural" binary-classifier output is (B, 1) → BCE. If you're fine-tuning a pretrained C-class backbone (ResNet, ViT, S3D, BERT), keep the C-class head and use CE — that's the canonical pattern across torchvision, transformers, and timm.

3Why "with logits" — the numerical-stability deep dive

The "with logits" form fuses the activation into the loss using the LogSumExp trick. The non-logits form computes the activation as a separate forward step, which can saturate in low precision.

The formula difference

FormComputationFailure mode
Without logits (binary) −[target · log(sigmoid(logit)) + (1−target) · log(1−sigmoid(logit))] sigmoid(logit) rounds to 0 or 1 in fp16/bf16 → log(0) = −inf → NaN gradients.
With logits (binary) −[target · z − log(1 + exp(z)) − (1−target) · log(1 + exp(z))] via LogSumExp Stable across the full float range. Never computes sigmoid or log as a separate step.
Without logits (multi-class) NLL(log_softmax(logits)) — two passes Same as binary: softmax entries can underflow to 0 in low precision, then log(0) = −inf.
With logits (multi-class) log_softmax + NLL fused; −(logit_c − LogSumExp(logits)) Stable. The LogSumExp subtracts the max logit before exponentiating, keeping all exp arguments ≤ 0.

What this means for mixed-precision training

If your forward pass runs under torch.autocast("cuda", dtype=torch.bfloat16) (or fp16), the model outputs are bf16. Without-logits losses then take a bf16 probability and apply log — the bf16 representation of sigmoid(z) for |z| > ~8 already saturates to 0 or 1, and log can't recover the information. The with-logits form sidesteps the saturated intermediate by computing the log-probability directly from the raw logit.

The math is invariant under fp32, so what?

Even when fp32 is enough for stability, the with-logits form is faster (one fused CUDA kernel vs two), supports native label smoothing and class weighting, and decouples the model from the loss (the model produces logits; the loss interprets them). The form choice has no downside except for legacy interop.

4BCE vs CE comparison — when the choice actually matters

Math is equivalent for binary classification, but the API and integration ergonomics differ.

Common pitfalls

  • Applying sigmoid/softmax in the model's forward when the loss expects logits. No PyTorch error — the loss silently computes the wrong thing (applies log-sigmoid to already-sigmoided values, badly mis-scaling gradients). Always: model produces logits, loss interprets them.
  • Using BCELoss with bf16/fp16 autocast. Trains fine for a few iterations, then produces NaN losses as logits drift to the saturating end of sigmoid. Symptom: train_loss goes to nan mid-epoch with no other warning. Fix: switch to BCEWithLogitsLoss.
  • Forgetting that CrossEntropyLoss targets are class indices, not one-hot. Passing one-hot float targets to CE produces a confusing error about expected long tensor; passing class indices to BCE produces a shape mismatch.
  • Class-weighted CE with the wrong index order. The weight tensor is indexed by class id, so weight=[1.0, pos_weight] assumes class 0 = negative, class 1 = positive. If your labels flip, the weighting silently inverts.
  • BCE's pos_weight ≠ CE's weight[1] mathematically. BCE's pos_weight multiplies only the positive-class log-likelihood; CE's per-class weight rescales the whole sample's contribution. Numerically similar at small imbalance, divergent at heavy imbalance.
  • Mixing the forms across the train/inference boundary. If training uses BCEWithLogitsLoss, inference must apply sigmoid on the model output to get probabilities. Forgetting this means downstream code interprets raw logits as probabilities — probably-wrong thresholds, broken precision-recall.
  • Conflating "single-output binary" with "two-output binary". Both are valid binary classifiers; they just match different losses. Don't try to use CrossEntropyLoss on a (B, 1) output — it errors. Don't try to use BCEWithLogitsLoss on a (B, 2) output — it computes the wrong thing.
